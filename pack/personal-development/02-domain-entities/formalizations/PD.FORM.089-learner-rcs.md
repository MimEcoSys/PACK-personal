# Формализация: Role Characterisation Space (RCS) Ученика

## 1. Назначение

### Четыре понятия — четыре разных вопроса

RCS использует четыре термина, которые отвечают на разные вопросы про Созидателя. Без этого различения они кажутся взаимозаменяемыми — но это не так.

| Вопрос | Термин | Пример |
|--------|--------|--------|
| **Из чего состоит Созидатель?** | **Узел** | Организм, Репозитории, Агенты |
| **В каком направлении он растёт?** | **Ось** | Мировоззрение / Мастерство (Пилот); БД / Программа (Машина) |
| **Что счита́ет машина автоматически из событий?** | **bh-характеристика** (bh. = behaviour) | bh.sys, bh.inv, bh.met — 7 метрик Аттестатора |
| **Как Диагност увидит потенциал в диалоге?** | **cp-срез** (cp. = capacity) | cp.rhy, cp.wld, cp.int — 13 срезов Диагноста |

Узел — физический объект. Ось — направление роста. bh-характеристика — непрерывный счёт поведения из событий. cp-срез — точечная оценка потенциала через рубрику. Четыре понятия, потому что четыре разных вопроса.

### Болид-онтология

Для диагностики система «человек + IWE» рассматривается через аналогию **Болида**: Пилот (биологический человек) + Машина (IWE). Созидатель — роль человека, а не этот составной носитель. Пилот, Машина и их рабочая связка развиваются по разным свидетельствам:

| Объект | Как развивается | Кто развивает |
|--------|-----------------|---------------|
| **Пилот** | Тренируется — наращивает Мировоззрение и Мастерство | Человек через программу ЛР |
| **Машина** | Строится — пополняются Pack, Среда, Агенты | Человек при проектировании IWE |
| **Болид** | Обкатывается — пилот и машина притираются в работе | Совместная практика реальных проектов |

**Развитие операционной проекции «человек ↔ IWE»** = развитие Пилота + создание IWE + проверка их совместной способности.

### Узлы Пилота

```
Человек (Пилот):
  Организм                          — тело, ритм, энергия
  Личность:
    Мыслительное мастерство         — картина мира, системные различения ← ЛР
    Прикладное мастерство:
      Мастерство саморазвития       — роль Ученика, M001–M008 ← ЛР
      Мастерство управления IWE     — ОРЗ-ритуалы, экзокортекс, агенты ← ЛР (cp.iwe)
      Мастерство создания IWE       — Pack-дизайн, новые методы, MCP-инструменты ← ЛР (cp.cre)
      Профессиональные методы       — методы предметной области (вне ЛР)
      Прочие прикладные мастерства  — спорт, язык, ремесло и т.д. (вне ЛР)
```

> **ЛР работает на четыре узла:** Мыслительное мастерство, Мастерство саморазвития, Мастерство управления IWE (cp.iwe), Мастерство создания IWE (cp.cre).
>
> Управление и создание IWE — **две независимые оси мастерства среды**. Развиваются параллельно: можно быть Пользователь-3 (уверенный пользователь) и одновременно Разработчик-0 (ещё не начал создавать) или Пользователь-3 + Разработчик-1 (уверенный пользователь + начинающий создатель). Обе оси — **рекомендательные**: используются Портным для контента и рекомендаций, но не блокируют ступень Ученика (см. §5).

### Узлы Машины

```
IWE (Машина):
  Репозитории (БД)                  — Pack и DS-файлы: формализованные знания
  Среда (Программа)                 — VS Code, Git, хуки, конфигурации, протоколы
  Агенты                            — модели + настройки + MCP-инструменты
```

### Оси роста

| Объект | Воздействие → Ось | Что меняется |
|--------|-------------------|--------------|
| **Пилот** | теория → **Мировоззрение** | Как видит себя, мир, роли |
| **Пилот** | методы → **Мастерство** | Что умеет делать устойчиво |
| **Машина** | информация → **БД** | Накопленные формализованные знания |
| **Машина** | инструменты → **Программа** | Среда, скрипты, агентные навыки |

### Петля управления (определение ступени)

С 31.10.2026 (решение пилота, РП-602, АрхГейт `DRR-archgate-stage-monotonic-no-gate`) ступень 1–4 присваивается **двумя независимыми путями**: расчётом по активности (Аттестатор) и диагностикой (Диагност). Присваивается большее значение. Диагностика повышает ступень, но не удерживает; ступень не понижается автоматически. Статус: решение принято 31.10; в боевом расчёте оно начнёт действовать после включения правила (РП-602 Ф11), до этого действует двойной gate v5.

```
bh-характеристики (Аттестатор, авто) → путь по активности → ступень
cp-срезы (Диагност, по запросу)      → путь по диагностике → ступень   (итог = большее)
```

1. Аттестатор считает ступень по активности (§13.3б) из событий Activity Hub и рабочих продуктов.
2. Диагност проводит диалог по ≤5 вопросам → оценивает потенциал по cp-срезам → даёт ступень по диагностике (§5.1).
3. Ступень 5 присваивается только диагностикой и составным gate (§5.2); расчёт по активности её не даёт.
4. Откат видит Аттестатор; ступень он не меняет, а сообщает участнику (§5.1).

**Что было и почему изменено.** До решения 31.10.2026 модель предписывала двойной gate (в боевом расчёте он действует до включения правила двух путей): итог = минимум из расчёта по активности и диагностики. Он защищал от ступени «по одной частоте действий», но удерживал растущих людей без уведомления: диагностика устаревает быстрее, чем человек растёт (случай 16–30.10.2026: уведомление об удержании не доставлялось). Расчёт по активности фиксирует частоту и объём поведения, диагностика видит потенциал; теперь каждый из них может повысить ступень сам, а ступень 5 как допуск остаётся за диагностикой.

### Два инструмента измерения

| Инструмент | Коды | Когда | Метод | Что измеряет |
|------------|------|-------|-------|--------------|
| **Аттестатор** (WP-310) | **bh.*** | Непрерывно, каждую неделю | SQL по Activity Hub, §12 | Поведение: частота, объём, регулярность |
| **Диагност** (MIM.R.009) | **cp.*** | По запросу, при расчёте ступени | ≤5 вопросов + рубрики §4, аудит артефактов | Потенциал: глубина понимания, качество ОРЗ |

### Проблема и решение

**Проблема.** PD.FORM.003 и PD.FORM.080 описывают ступени Ученика (1 Случайный → 5 Проактивный) как плоские нарративные состояния. При диагностике живого человека решение «ступень = N» не воспроизводимо — два диагноста могут прийти к разным ступеням.

**Решение.** Перейти к **многомерному профилю** по формализму FPF A.19 `U.CharacteristicSpace`. Разделить автоматические bh-метрики (Аттестатор) и диагностические cp-срезы (Диагност). Ступень вычисляется из профиля явным правилом (§5).

**Три эффекта:**
1. **Диагностика воспроизводима.** Алгоритм: bh-сигнал → cp-рубрики → ступень + bottleneck.
2. **Видно слабое звено.** Bottleneck определяет фокус на квартал.
3. **RCS-часть составного gate Д→П** формализована как ступень 4 по §5.1 плюс cp-часть §5.2; полный gate ступени 5 дополняют две проверки PD.FORM.093 (§5.2).

## 2. Структура RCS: 13 cp-срезов (диагностика Диагноста)

> **Принцип.** Каждый cp-срез диагностирует конкретный узел Созидателя через рубрику 1-5. Срез ≠ узел: узел = физический объект, срез = инструмент измерения потенциала.
>
> **TTL правило.** Четыре стержневых среза `cp.rhy`, `cp.wld`, `cp.skl`, `cp.int` имеют срок действия **6 месяцев** и должны быть свежими для подтверждения текущей ступени или любого повышения. С 20.10.2026 то же относится к `cp.agt`: он входит в минимум на всех ступенях (решение пилота, §5.1). Просроченный стержневой профиль даёт неопределённую текущую оценку и требует повторной диагностики; исторически достигнутая ступень при этом не стирается.

| Код | Срез | Что диагностирует | Узел | Статус |
|-----|------|-------------------|------|--------|
| **cp.rhy** | Ритмичность | Регулярность практики: частота, ритм, восстановление после срыва | Организм | **mandatory** |
| **cp.wld** | Мировоззрение | Зрелость системного взгляда (мировоззренческая дуга FORM.080 §3) | Мыслительное мастерство | **mandatory** |
| **cp.skl** | Мастерство саморазвития | Владение M001–M008: глубина и автоматизм применения | Мастерство саморазвития | **mandatory** |
| **cp.iwe** | Управление IWE | ОРЗ-ритуалы, Pack/DS-структуры, маршрутизация знаний, Week/Month Close | Мастерство управления IWE | informational (рекомендательная ось) |
| **cp.int** | Системное мышление | Применение различений: роль, система, граница, эмерджентность | Мыслительное мастерство | **mandatory** |
| **cp.agt** | Агентность | Доля самоинициированных действий, независимость решений | Поведенческий gate (§5.2) | **mandatory** (с 20.10.2026; до этого — только переход 4→5) |
| **cp.cre** | Создание IWE | Pack-дизайн, MCP-инструменты, расширения протоколов | Мастерство создания IWE | informational (рекомендательная ось) |
| **cp.knw** | Системное знание | Владение SoTA-методами домена | Профессиональные методы | informational |
| **cp.env** | Среда и окружение | Осознанное управление физической и цифровой средой | Среда (IWE.Среда) | informational |
| **cp.auto** | Автопилот | Глубина использования AI-агентов как автопилота | Агенты (IWE.Агенты) | informational |
| **cp.exo** | Экзоскелет | Использование IWE как усилителя мышления, не замены | Среда + Агенты | informational |
| **cp.cult** | Культура и передача | Передача методов и мировоззрения другим | Надсистема (сообщество) | informational |
| **cp.traj** | Траектория и рефлексия | Осознанное управление собственным путём развития | Личность (рефлексия) | informational |

**Обязательные для расчёта ступени:** cp.rhy, cp.wld, cp.skl, cp.int, cp.agt (агентность — в минимуме на всех ступенях с 20.10.2026).
**Информационные (профиль, не блокируют):** cp.iwe, cp.cre, cp.knw, cp.env, cp.auto, cp.exo, cp.cult, cp.traj.

> **Решение v5.0 (17 мая 2026):** cp.iwe и cp.cre — две независимые оси мастерства IWE — переведены из mandatory в informational. Причина: лестница ступеней Ученика (5 нарративных уровней зрелости) и стадии мастерства IWE (две оси × 3 имени: Пользователь 1-3 / Разработчик 1-3) — разные шкалы. Жёсткий gate на cp.iwe смешивал их. Теперь Портной использует cp.iwe и cp.cre как **рекомендательные оси** для контента (см. §6.3). Ступени 1–4 ограничивает стержневой профиль `cp.rhy`/`cp.wld`/`cp.skl`/`cp.int`; `cp.agt` дополнительно блокирует только переход 4→5. *(Заменено решением пилота 20.10.2026: `cp.agt` входит в минимум на всех ступенях, §5.1.)*

## 3. Квартет каждого среза (по PD.FORM.088 §2)

Каждый cp-срез = четвёрка:

| Элемент | Что фиксируется |
|---------|-----------------|
| **Характеристика** | Свойство системы-человека как аспект внимания |
| **Показатель** | Выбранная шкала и единица измерения |
| **Значение** | Два числа: **сейчас** (моментальное) и **baseline** (устойчивый уровень, сглаживание 4-8 недель) |
| **Потенциал** | Лучшее показанное значение с записью условий показа, ведётся по носителю (решение пилота 20.11.2026, п.13; `PD.FORM.088` §2) |

**Правило формулировки цели:** любая цель программы ЛР в рамках среза обязана называть, что двигаем:
- «Поднять **baseline** среза cp.rhy с N до M за квартал» → cp.skl/cp.iwe (методы)
- «Расширить **потенциал** среза cp.int с N до M за год» → cp.wld/cp.int (фундаментальное развитие)

Цель, сформулированная через «значение-сейчас», отбрасывается как реакция на шум (PD.FORM.088 §2.1).

## 4. Определения cp-срезов

> **Ограничение MVP:** конкретные шкалы и пороги — draft. Финальная версия со всеми тестовыми заданиями и алгоритмом измерения — следующая итерация (§9 Roadmap).

### cp.rhy — Ритмичность

| Элемент | Значение |
|---------|----------|
| Характеристика | Регулярность практики саморазвития: ритм, частота, восстановление |
| Показатель | Среднее дней/нед практики (скользящее 4-8 нед) + max разрыв |
| Значение (сейчас) | Дней/нед текущей недели |
| Значение (baseline) | Скользящее среднее 4-8 недель |
| Потенциал | Ежедневная практика как стиль жизни, max разрыв ≤1 дня |

**Рубрики baseline-индексов 1-5.**

| Индекс | Дн/нед | Операционные признаки baseline |
|--------|:------:|--------------------------------|
| **1** | ~1-2 | Случайные всплески. Нет паттерна недели. Срывы на месяцы. Восстановление ≥ месяца |
| **2** | ~3 | Пробует регулярность. Минимум 1-2 фиксированных слота в неделю. Срывы 2-3 нед, восстановление 2-3 нед |
| **3** | ~5 | Устойчивый недельный ритм. Срывы короткие (≤2 нед), восстановление ≤1 нед. Практика — привычка, не усилие воли |
| **4** | ~6 | Высокая регулярность. Редкие срывы (≤7 дней). Ритм адаптируется к контексту (командировки, аврал) — не разрушается |
| **5** | ~6.7+ | Ежедневная практика как стиль. Пропуск ≤1-2 дня/мес. Ритм передаётся — способен поддержать другого в построении ритма |

### cp.wld — Мировоззрение

| Элемент | Значение |
|---------|----------|
| Характеристика | Зрелость системного мировоззрения |
| Показатель | Фаза мировоззренческой дуги (FORM.080 §3), индекс 1-5 |
| Значение (сейчас) | Текущая фаза по ответам в диалоге |
| Значение (baseline) | Фаза, устойчиво проявляющаяся 4+ нед в артефактах |
| Потенциал | 5 (системное мировоззрение + agency) |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Проблемы объясняет внешними обстоятельствами. Нет языка системы/метода. Артефакты: отсутствуют или чисто событийные |
| **2** | Видит внутренние ресурсы: внимание, энергия, ритм. Различает «состояние» и «задачу». В речи: «я собран/не собран», «у меня не было ресурса» |
| **3** | Замечает влияние среды (люди, мемы, пространство). В речи: «окружение тянет», «я попал под влияние». Артефакты: записи о влиянии среды |
| **4** | Описывает задачи через роли, границы, интерфейсы. Различает «я» и «моя роль». В речи: «я как [роль]», «обещание системы». Артефакты: системные разборы ситуаций |
| **5** | Интегрированное системное мировоззрение + agency. Создаёт культурные формы. В речи: «мы как система». Артефакты: наставничество, публикации, инициативы |

**Расхождение с §13.1.3 (21.11.2026, РП-576 Ф6.2).** Рубрика описывает содержание картины мира по фазам дуги, а определение зрелости — качество оснований решений. Индекс 4 («роли, границы, интерфейсы») описывает системность (`cp.int`), индекс 5 включает агентность и охват («наставничество, публикации»). Рубрика сохраняется до замены по паспорту шкал (РП-151, Часть 7); вопрос диагностики — у его владельца (РП-385).

### cp.skl — Мастерство саморазвития

| Элемент | Значение |
|---------|----------|
| Характеристика | Глубина и автоматизм применения методов M001–M008 |
| Показатель | Уровень освоения методов: знает / применяет эпизодически / применяет системно / учит других |
| Значение (сейчас) | Применяемые методы текущей недели |
| Значение (baseline) | Устойчиво встроенные методы (6+ нед применения) |
| Потенциал | Все методы ЛР как автоматизированный стиль + способность передать |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Методы ЛР (M001-M008) неизвестны или известны формально. Работа по интуиции и привычке. Нет учёта времени, слотов или Day Open/Close |
| **2** | Знает 2-3 метода ЛР. Применяет помидорки или Day Open/Close эпизодически. Держит ритм 2-3 нед, потом срыв. Восстановление — несколько недель |
| **3** | 4-6 методов ЛР применяет устойчиво. Помидорки/слоты как привычка. Day Open/Close регулярно. Восстановление после срыва — ≤1 нед |
| **4** | Полный стек M001-M008 применяется автоматически. Методы встроены в ежедневный режим без напоминаний. Понимает граничные случаи применения |
| **5** | Методы ЛР — стиль жизни. Адаптирует методы под свой контекст. Способен передать метод другому и поддержать его освоение |

**Что мерит срез (21.11.2026, РП-576 Ф6.5).** Срез мерит средство — глубину и автоматизм применения методов; сдвиг самих характеристик (результат) мерит шкала общего наращивания (паспорт шкал РП-151, Часть 10). Оба — разные измерения узла «мастерство саморазвития» (`01B` D.152), один другим не заменяется: применение метода ≠ достигнутый рост. В рубрике есть признаки других шкал: «восстановление после срыва ≤1 нед» (индексы 2–3) — стрессоустойчивость; «Day Open/Close регулярно» — собранность и регулярность; «способен передать метод» (индекс 5): передача метода может свидетельствовать о владении им, масштаб адресатов передачи — охват (§13.1, общие правила п.3).

### cp.iwe — Управление IWE

| Элемент | Значение |
|---------|----------|
| Характеристика | Владение рабочей средой: ОРЗ-ритуалы, Pack/DS-структуры, маршрутизация знаний, управление памятью, конфигурация агентов |
| Показатель | Зрелость экзокортекса: доля задач через ОРЗ + наличие Pack/DS + активность Week/Month Close |
| Значение (сейчас) | % задач за неделю через ОРЗ |
| Значение (baseline) | Устойчивая доля + зрелые артефакты (WP-контексты, captures, Week/Month Close) |
| Потенциал | 100% значимых задач через ОРЗ + полная IWE-инфраструктура |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | ОРЗ не применяется. Задачи без явного Открытия/Закрытия. Экзокортекса нет (возможно, есть бот как канал). Артефакты случайны и не связаны. Нет WP-контекстов |
| **2** | Open/Close применяются эпизодически (<30% значимых задач). Начата Pack- или DS-структура, слабо заполнена. 1-2 WP-контекста. Day Open/Close — нерегулярно. Week Close — нет |
| **3** | ОРЗ на значимых задачах (>60%). Day Open/Close — регулярно. Pack и DS структурированы по шаблонам. 5+ WP-контекстов. Week Close — регулярно. Memory-файлы обновляются |
| **4** | ОРЗ как норма (>90%). Протоколы «на автомате». Зрелый экзокортекс: Pack с 10+ формализациями, DS с чётким routing. Month Close как ритуал с явным циклом обратной связи. Субагенты применяются |
| **5** | 100% значимых задач через ОРЗ. Свои расширения протоколов, задокументированные для других. Передаёт метод. Экзокортекс — полная инфраструктура: Pack, DS, FMT-шаблоны, staging-канал |

**Имя стадии мастерства IWE — функция ступени Ученика, не cp-индекса.**

cp.iwe-индекс (1-5) измеряет **факт** освоения управления средой по операционным признакам выше. Имя стадии («Пользователь-1», «Разработчик-2» и т.д.) — это **ожидаемое имя на каждой ступени Ученика**, единое для двух осей IWE (cp.iwe и cp.cre). Полная таблица — в §6.3.

Краткая привязка (см. §6.3 для полной таблицы и логики):

| Ступень Ученика | Стадия мастерства IWE |
|:---:|:---|
| 1 Случайный | **Пользователь-1** |
| 2 Практикующий | **Пользователь-2** |
| 3 Систематический | **Пользователь-3 + Разработчик-1** (одновременно — переходная точка) |
| 4 Дисциплинированный | **Разработчик-2** |
| 5 Проактивный | **Разработчик-3** |

> **Source-of-truth:** имена стадий определены **здесь и в §6.3**. Реализация в коде — общий модуль `DS-autonomous-agents/scripts/iwe_stage_names.py`, импортируется `iwe-stage-controller.py` и `render-pilot-guides.py`. **Имя стадии не выводится из cp.iwe-индекса — оно задаётся ступенью Ученика.**

> **Связь со ступенью Ученика — рекомендательная.** На ст.3 Ученика (Систематический) ожидаемый профиль = cp.iwe ≥ 3 (Пользователь-3). Если cp.iwe < 3 — Портной рекомендует подтянуть управление средой. cp.iwe **не блокирует** ступень — это рекомендательная ось.

### cp.int — Системное мышление

| Элемент | Значение |
|---------|----------|
| Характеристика | Способность к системному взгляду и системному разбору |
| Показатель | Применение различений (роль, система, граница, эмерджентность, деятельность) в разборе реальных ситуаций |
| Значение (сейчас) | Сколько различений применил в недельных задачах |
| Значение (baseline) | Стабильно применяемые различения |
| Потенциал | Интегративная сложность + калибр задач, которые способен удержать |

**Рубрики baseline-индексов 1-5.** Измеряется разбором реальных ситуаций (не тест-викториной).

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Различения не применяются. Язык бытовой, проблемы объясняются нарративами. Путает систему с группой людей, роль с должностью |
| **2** | Применяет 1-2 базовых различения (система vs процесс, метод vs инструмент). Частые ошибки. В незнакомой области — беспомощен |
| **3** | Применяет 5-7 различений стабильно в знакомых контекстах. Находит роли, границы, интерфейсы. В новом контексте — нужен образец |
| **4** | Применяет 10+ различений в новых ситуациях без образца. Самостоятельно находит неочевидные системы. Конструктивно критикует чужие разборы |
| **5** | Интегрированное системное мышление. Создаёт новые различения. Удерживает калибр больших систем. Передаёт метод — обучает системному разбору |

**Оговорка (21.11.2026, РП-576 Ф6.2).** Вопрос диагностики по этому срезу — самооценка, хотя рубрика требует разбора реальных ситуаций; «передаёт метод» в индексе 5: передача метода может свидетельствовать о владении им, масштаб адресатов передачи — охват (§13.1, общие правила п.3).

### cp.agt — Агентность

| Элемент | Значение |
|---------|----------|
| Характеристика | Способность инициировать изменения, действовать автономно |
| Показатель | Доля самоинициированных действий vs реактивных (задания от окружения) |
| Значение (сейчас) | % за неделю |
| Значение (baseline) | Устойчивая доля + наличие собственных проектов (не заимствованных) |
| Потенциал | ≥80% самоинициированных (Проактивный, FORM.087) |
| Способ сбора (сейчас) | Самооценка: вопрос 5 диагностики (скилл `/diagnose`, у бота тот же вопрос). Ответ 5 («определяю, чем занимаются другие») описывает охват, а не уровень агентности (§13.1, общие правила п.3). Уточняющий вопрос по этому срезу — самооценка ответственности за результат; его ответ заменяет значение среза, ответ 5 («задаю планку для других») — тоже охват. Добавлено 21.11.2026 (РП-576 Ф6.1) |
| Признак самоинициированного (целевой) | Доля решения человека по §13.1.2. В текущем вопросе и в событиях этого признака нет: срез мерит самооценку доли действий, долю решения не подтверждает |

**Агентность в минимуме.** С 20.10.2026 `cp.agt` входит в минимум пяти обязательных срезов на всех ступенях (§5.1, §5.2): без свежего `cp.agt` ступень по диагностике не считается, для ступени 5 нужна пятёрка. Уже сохранённую `attained_stage` срез не понижает.

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Действует почти исключительно по запросу. Собственных проектов нет. Решения откладываются — ждёт разрешения или чужой инициативы. В речи: «мне сказали», «когда можно будет» |
| **2** | Есть 1-2 личных намерения. Инициирует мелкие изменения. Большинство задач — от окружения. Решения принимает медленно, часто запрашивает одобрение |
| **3** | ~50% задач из собственных целей. Держит один свой фокус на несколько недель (проект не обязателен). Принимает решения в знакомых контекстах без подтверждения. В незнакомом — нужен образец |
| **4** | >60% самоинициировано. Несколько независимых проектов. Действует в неопределённости: ставит эксперимент, оценивает, корректирует |
| **5** | >80% действий собственные. Формирует повестку для ближнего круга. Инициирует изменения в системах без формальной власти. Создаёт условия, в которых другие становятся проактивными |

> **Решение пилота 29.10.2026 (РП-385):** на индексе 3 признак — один свой фокус, удерживаемый несколько недель; наличие проекта для него не важно. Прежняя формулировка «держит один активный личный проект» делала признак недостижимым там, где проект не требуется.

### cp.cre — Создание IWE

| Элемент | Значение |
|---------|----------|
| Характеристика | Глубина вклада в расширение IWE-инфраструктуры (Pack, инструменты, протоколы) |
| Показатель | Уровень авторского вклада: от использования готового до создания нового для других |
| Значение (baseline) | Устойчиво применяемые паттерны создания IWE-компонентов |
| Потенциал | Создаёт шаблоны и инструменты, которые используют другие |

> **Рекомендательная ось.** cp.cre — информационный срез, не блокирует ступень Ученика. Первая безопасная модификация личной IWE начинается с первого дня S1: участник создаёт собственную заметку, именованный браузерный диалог и правила их связи с внешним проектом. На ст.3+ начинается систематическое создание структуры, Pack-разделов и автоматизаций; после отдельного старта РР это мастерство может углубляться на рабочих контурах. Портной использует cp.cre для рекомендации перехода от пользования средой к её осознанной перестройке.

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Использует только готовые шаблоны IWE без изменений. Не создаёт Pack-разделов |
| **2** | Незначительные кастомизации (settings, переименование файлов). Начата Pack-структура по шаблону |
| **3** | Создаёт собственные Pack-разделы (02-domain-entities). Использует базовые MCP-инструменты. Расширяет протоколы через extensions/ |
| **4** | Проектирует Pack-домены с нуля. Пишет MCP-скрипты, хуки. Создаёт staging-канал для своих правил |
| **5** | Создаёт FMT-шаблоны или MCP-серверы для других. Публикует методы создания IWE. Обучает созданию IWE |

**Имя стадии — функция ступени Ученика (см. §4 cp.iwe и §6.3).**

cp.cre-индекс (0-5) измеряет **факт** освоения создания среды по операционным признакам выше. Имя стадии («Разработчик-1», «Разработчик-2», «Разработчик-3») берётся из таблицы §6.3 по ступени Ученика, не из cp.cre-индекса. На ст.1-2 именованная стадия остаётся «Пользователь», но `cp.cre` не обязано быть нулём: собственная заметка, безопасная настройка браузерного диалога и простое правило маршрутизации уже являются начальными следами создания. Ст.3 обозначает переход к систематическому созданию, ст.4-5 — развитую перестройку IWE.

> **Связь со ступенью Ученика — рекомендательная.** Имя стадии («Пользователь-N» / «Разработчик-N») берётся из таблицы §6.3 по ступени Ученика. Уже на ст.1 Портной предлагает минимальное создание IWE на безопасном личном проекте; на ст.3+ при `cp.cre = 0` рекомендует систематическую кастомизацию и первые Pack-разделы. cp.cre **не блокирует** ступень.

| **5** | IWE — бесшовное продолжение мышления. Результаты всегда объяснимы без «ИИ подсказал». Обучает других экзоскелетному мышлению |

### cp.cult — Культура и передача

| Элемент | Значение |
|---------|----------|
| Характеристика | Осознанная передача методов, мировоззрения и культуры развития другим |
| Показатель | Уровень системности культурной передачи (от нулевой до создания культурной инфраструктуры) |
| Значение (baseline) | Устойчивые паттерны передачи — не разовые объяснения |
| Потенциал | Создаёт культурную инфраструктуру (программы, шаблоны), которую используют без участия автора |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Не передаёт методы другим. Практика — только личная |
| **2** | Делится неформально по запросу: объясняет метод знакомому. Нет системы |
| **3** | Менторит 1-2 человек. Создаёт заметки/инструкции для других. Публикации (хотя бы личный канал) |
| **4** | Систематическая передача знаний: программа онбординга, публичные публикации, воркшопы |
| **5** | Создаёт культурную инфраструктуру: курсы, шаблоны IWE, обучает тренеров. Влияние масштабируется без личного участия |

### cp.traj — Траектория и рефлексия

| Элемент | Значение |
|---------|----------|
| Характеристика | Осознанное управление собственным путём развития: постановка горизонтов, рефлексия прогресса, коррекция курса |
| Показатель | Уровень осознанности и системности в управлении собственной траекторией |
| Значение (baseline) | Устойчивые ритуалы рефлексии о прогрессе (не просто делать — видеть куда идёшь) |
| Потенциал | Долгосрочная траектория с горизонтами + способность помочь другим проектировать траекторию |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Нет рефлексии о собственном развитии. «Что получилось — то и получилось» |
| **2** | Периодический ретроспективный взгляд по запросу. Реагирует на события, а не управляет курсом |
| **3** | Регулярный Week Close с анализом прогресса. Видит динамику. Корректирует план на основе итогов |
| **4** | Month/Quarter Close + Strategy Session. Управляет горизонтами (нед/квартал/год). Видит паттерны роста и торможения |
| **5** | Осознанное долгосрочное траектория-проектирование. Менторит других в проектировании траектории. Передаёт культуру рефлексии |

## 5. Правила вычисления ступени (composition rule)

### 5.1 Два независимых пути присвоения ступени (Аттестатор и Диагност)

> **Статус:** решено 31.10.2026, в боевом расчёте не включено (РП-602 Ф11); сегодня действует двойной gate v5 (§13.6).

```
1. Путь по активности (Аттестатор): свёртка §13.3 над характеристиками набора §13.3б, измеряемыми поведением.
2. Путь по диагностике (Диагност): ≤5 вопросов по cp-срезам → cp-профиль; ступень = cp_floor, где cp_floor — минимум пяти обязательных срезов (cp.rhy, cp.wld, cp.skl, cp.int, cp.agt).
3. Для ступеней 1–4 присваивается большее из двух значений; низкий результат одного пути не блокирует другой.
4. Ступень не понижается автоматически; она означает «достигнуто».
5. Ступень 5 — только через диагностику и составной gate §5.2.
```

**Скачок на несколько ступеней допустим (решение пилота 31.10.2026 по теневому прогону на 55 участниках с согласием на отслеживание).** Диагностика поднимает ступень без ограничения на число ступеней; проверенный вариант «не выше активности плюс одна ступень» отклонён. Расчёт ступени идёт только по участникам, давшим согласие на отслеживание поведения.

**Агентность в минимуме на всех ступенях (решение пилота 20.10.2026, РП-576 — как в коде, `cp_assessment.compute_cp_stage`).** Прежняя редакция брала для ступеней 1–4 минимум только четырёх стержневых срезов, а `cp.agt` проверяла лишь на переходе 4→5.

**Откат (31.10.2026).** Путь по активности даёт ступень ниже текущей четыре еженедельные оценки подряд. Пока откат виден, раз в неделю участнику уходит сообщение «видим откат, пройдите диагностику снова»; ступень не меняется. Сообщение прекращается, когда путь по активности вернулся на текущую ступень. Участник, у которого нет сигнала активности, откатом не считается. Прежний принцип «bh-сигнал не может быть выше cp-профиля» снят: человек с высокой систематичностью (bh.sys=5) и слабым мировоззрением (cp.wld=2) получает ступень по активности, а диагностика остаётся самостоятельным путём вверх.

**Административный старт ≠ подтверждённая текущая ступень.** После зачисления участник входит в учебный нарратив ступени 1 «Случайный» и может выполнять входные задания сразу. Это хранится как состояние участия (`program_participation_status = enrolled`) и `narrative_start_stage = 1`, но само по себе не записывает `current_stage = 1`. Первая текущая оценка по пути активности требует полного 7-дневного окна bh-наблюдений без разрыва телеметрии; по пути диагностики — свежих значений всех четырёх стержневых cp-срезов. Пути независимы: первая ступень может прийти любым из них. До этого `current_stage = None`, `stage_evaluation_status = indeterminate`.

### 5.2 Составной gate перехода 4→5: Проактивный и готовность к РР

> **Общая граница программ по активной PD.FORM.003 §5:** ступень 4 — базовое завершение ЛР. Ступень 5 — продвинутое завершение ЛР для тех, кто дорос до Проактивного внутри этой программы, и одновременно готовность/допуск к РР. Gate подтверждает ступень и готовность, но не зачисление и не фактический старт РР.
>
> **Полный тройной gate:** (i) ступень 4 по §5.1 и cp-часть ниже (§12.3 для присвоения с 15.10.2026 не применяется, приёмка 20.10); (ii) метрический gate переходного профиля с уверенностью не ниже medium, рассчитанной только по пяти обязательным характеристикам (PD.FORM.093 §§5.4, 7.1); (iii) свежее подтверждение изменения на уровне охвата не ниже 2 (PD.FORM.093 §7.2: confidence ≥ medium, изменение и диагностическая сессия ≤3 месяцев).

**Cp-часть RCS-gate:** для перехода ст. 4 → 5:
- **Стержневой gate:** cp.rhy = 5, cp.wld = 5, cp.skl = 5, cp.int = 5
- **Agency gate:** cp.agt = 5 (устойчивая доля самоинициированных действий)

> **Решение пилота 20.10.2026 (РП-576, пир-сессия `2026-10-20-14-wp576-sh2-stage-bridge`): правило — как в коде.** Подтверждённая диагностикой ступень = минимум пяти обязательных срезов (`cp.rhy`, `cp.wld`, `cp.skl`, `cp.int`, `cp.agt`; `activity_hub/cp_assessment.py::compute_cp_stage`), поэтому ступень 5 требует пятёрок по всем пяти. Прежняя редакция (≥ 4 по каждому) — мягче фактического поведения; заменена.
- **TTL gate:** все blocking cp-срезы диагностированы ≤6 месяцев назад
- **cp.iwe и cp.cre — не в gate.** Используются Портным для рекомендаций (см. §6.3), не блокируют переход.

**Гейт ступени ≠ гейт зачисления в конкретную РР.** Программа рабочего развития может отдельно потребовать показать операционный цикл в своей ИИ-среде: самостоятельно войти в среду, сформулировать реальную работу и критерий результата, ограниченно делегировать ИИ, сохранить решения и контекст, независимо проверить ответ, восстановиться после прерывания и предъявить результат со свидетельствами. Эта проверка не входит в `stage5_gate_status`, не меняет `current_stage`/`attained_stage` и не превращает `cp.iwe` или `cp.cre` в блокирующие срезы.

```python
CORE_CP = ('rhy', 'wld', 'skl', 'int')
def cp_is_fresh(slice_code):
    slice_value = cp.get(slice_code)
    return (
        slice_value is not None
        and type(slice_value.baseline_idx) is int
        and 1 <= slice_value.baseline_idx <= 5
        and slice_value.assessed_at is not None
        and slice_value.assessed_at >= now() - interval('6 months')
        and slice_value.assessed_at <= now()
    )

core_cp_fresh = all(cp_is_fresh(slice_code) for slice_code in CORE_CP)
cp_agt = cp.get('agt')
cp_agt_fresh = cp_agt is not None and cp_is_fresh('agt')
core_cp_known_failure = any(
    cp_is_fresh(slice_code) and cp[slice_code].baseline_idx < 5
    for slice_code in CORE_CP
)
cp_agt_known_failure = cp_agt_fresh and cp_agt.baseline_idx < 5
CP_FLOOR_SLICES = CORE_CP + ('agt',)
cp_floor = (
    min(cp[slice_code].baseline_idx for slice_code in CP_FLOOR_SLICES)
    if core_cp_fresh and cp_agt_fresh else None
)
# Количество последовательных полностью наблюдаемых календарных дней,
# заканчивающихся текущим днём; отсутствие событий допустимо, разрыв ingestion — нет.
bh_signal_evaluable = (
    bh_observation_window_days >= 7
    and activity_hub_ingestion_complete IS TRUE
    and type(recommended_stage) is int
    and 1 <= recommended_stage <= 5
)

stage5_cp_gate_status = (
    'not_passed' if core_cp_known_failure or cp_agt_known_failure else
    'indeterminate' if not core_cp_fresh or not cp_agt_fresh else
    'passed'
)
stage5_bh_gate_status = (
    'indeterminate' if not bh_signal_evaluable else
    'passed' if recommended_stage >= 5 else
    'not_passed'
)

stage5_gate_status = (
    'not_passed' if stage5_bh_gate_status == 'not_passed'
        or stage5_cp_gate_status == 'not_passed'
        or form093_metric_gate_status == 'not_passed'
        or form093_real_change_gate_status == 'not_passed' else
    'indeterminate' if stage5_bh_gate_status == 'indeterminate'
        or stage5_cp_gate_status == 'indeterminate'
        or form093_metric_gate_status == 'indeterminate'
        or form093_real_change_gate_status == 'indeterminate' else
    'passed' if stage5_bh_gate_status == 'passed'
        and stage5_cp_gate_status == 'passed'
        and form093_metric_gate_status == 'passed'
        and form093_real_change_gate_status == 'passed' else
    'not_passed'
)
stage5_gate_passed_now = stage5_gate_status == 'passed'

if not bh_signal_evaluable or cp_floor is None:
    candidate_stage = None
    stage_evaluation_status = 'indeterminate'
else:
    candidate_stage = 5 if stage5_gate_passed_now else min(recommended_stage, cp_floor, 4)
    stage_evaluation_status = 'confirmed'

current_stage = candidate_stage
attained_stage = (
    previous_attained_stage
    if candidate_stage is None
    else max(previous_attained_stage or candidate_stage, candidate_stage)
)

rr_readiness_status = (
    'ready' if current_stage == 5 and stage5_gate_passed_now else
    'revalidation_required' if attained_stage is not None and attained_stage >= 5 else
    'reassessment_required' if stage5_gate_status == 'indeterminate' else
    'not_ready'
)
rr_ready_at_start = current_stage == 5 and stage5_gate_passed_now
```

**Раздельные состояния.** `candidate_stage` и равное ему `current_stage` показывают текущее состояние, подтверждаемое свежими данными; при неполном 7-дневном bh-окне, разрыве телеметрии либо просроченном/неполном стержневом cp-профиле оба равны `None`, а `stage_evaluation_status = indeterminate`. Отдельный `stage5_gate_status` сохраняет различие между непройденным и пока неоцениваемым переходом 4→5. `attained_stage` — монотонно хранимая исторически достигнутая ступень ученика, а не квалификация; до первой подтверждённой оценки `previous_attained_stage` и `attained_stage` равны `None`. Поэтому истечение TTL или временная просадка может понизить текущую оценку либо сделать её неопределённой, но не отменяет исторически достигнутую ступень. Жизненный цикл ЛР хранит четыре независимых факта: `lr_basic_result_achieved_at` (впервые подтверждена ступень 4), `lr_advanced_result_achieved_at` (впервые подтверждена ступень 5), `lr_program_completed_at` (участник фактически завершил выбранную траекторию) и `lr_completion_stage ∈ {4, 5}` (ступень на момент завершения). Если участник остаётся в программе после ступени 4, завершение можно записать уже на ступени 5. Если он завершил программу на ступени 4, последующее достижение ступени 5 фиксируется как продвинутый milestone и не переписывает исторический факт выпуска.

На момент успешной оценки ступени 5 действует `rr_readiness_status = ready`, но это не бессрочный допуск: перед фактическим стартом РР заново проверяется полный gate, включая TTL блокирующих cp-срезов и свежесть доказательства реального изменения. Истёкшие или просевшие данные дают `revalidation_required`, а не ретроактивное понижение ступени. `rr_started` остаётся отдельным историческим событием и записывается только при `rr_ready_at_start = true`.

### 5.3 Bottleneck

**Bottleneck ступеней 1–4** = cp-срез с минимальным индексом среди четырёх стержневых:

```
bottleneck = argmin(cp.rhy, cp.wld, cp.skl, cp.int).baseline_idx
```

Навигатор и Портной используют bottleneck для фокуса контента на квартал. При подготовке перехода 4→5 низкий `cp.agt` показывается отдельно как **transition blocker**, но не понижает уже подтверждённую ступень 4.

> **cp.iwe и cp.cre не входят в bottleneck**, но Портной отдельно анализирует имена стадий мастерства IWE (Пользователь 1-3 / Разработчик 1-3) и даёт рекомендации по их развитию — см. §6.3.

### 5.4 Информационные cp-срезы не блокируют ступень

cp.iwe, cp.cre, cp.knw, cp.env, cp.auto, cp.exo, cp.cult, cp.traj — **профиль, не ступень**. Они влияют на:
- Рекомендации Навигатора
- Контент Портного (cp.iwe и cp.cre → имена стадий мастерства IWE, см. §6.3)
- Выбор канала (cp.auto → глубина автопилота)

> **Оси мастерства IWE (cp.iwe, cp.cre) — особый случай информационных срезов:** имеют именованные стадии (Пользователь 1-3 / Разработчик 1-3) и маркеры связи со ступенью Ученика. Это рекомендательная двумерная карта развития мастерства среды, отображаемая Портным в персональном руководстве.

## 6. Применение ролями платформы

### 6.1 Диагност (MIM.R.009 / DP.ROLE.042)

**Алгоритм: три фазы, шесть вопросов и до одного уточняющего** (пять обязательных срезов + информационный `cp.iwe`; РП-385 Ф18, 15.11.2026).

#### Граница пользовательского текста — обязательна для любого интерфейса

Диагност ведёт разговор обычным языком. В сообщениях человеку запрещено показывать внутренние коды и поля (`cp.*`, `bh.*`, `bottleneck_slot`, `recommended_stream`, `skip_to_stage`), имена таблиц, программные выражения и служебные названия вроде TTL/CAT/RCS. Их используют только при вычислении и записи результата.

- Вопросы задаются **по одному**. Нельзя заранее выводить весь опрос, все рубрики или инструкцию «добавьте артефакт к каждому баллу».
- Перед первым вопросом достаточно сказать: «Я задам шесть коротких вопросов, по одному за раз, и иногда один уточняющий. Выберите ближайший вариант; если ни один не подходит или вы затрудняетесь выбрать, ответьте своими словами. Под практикой здесь понимается конкретная работа над собой: планирование, ведение записей, применение выбранного способа или разбор результата. Под итогом — короткая проверка, что получилось и что изменить».
- Числа 1–5 допустимы только как удобные варианты текущего вопроса. После выбора Диагност отвечает человеческим подтверждением, а не повторяет код среза.
- «Артефакт» в пользовательском тексте заменяется конкретным примером: запись учёта времени, недельный итог, разбор решения или законченная работа.
- `bottleneck` называется «приоритетом роста» или «тем, что сейчас сильнее всего ограничивает следующую ступень».
- Результат сохраняется «в профиле развития IWE». Техническое имя хранилища человеку не показывается.
- Ограничение повторной диагностики объясняется так: «Повторную диагностику обычно проводят не чаще одного раза в семь дней, чтобы кратковременное настроение не искажало результат». Слово «кулдаун» не используется.
- Если дата прошлой оценки недоступна, не перекладывать техническую проверку на человека длинным предупреждением. Задать один короткий вопрос: «Вы проходили эту диагностику в последние семь дней?» При ответе «да» показать текущий результат и предложить вернуться позже; при «нет» продолжить.
- Вопрос об инициативе (`cp.agt`) задаётся каждому: агентность входит в минимум на всех ступенях (решение пилота 20.10.2026). Прежнее правило «только при проверке перехода 4→5» отменено этим решением.
- Тексты вопросов должны проходить реестр понятий и родов: задача и ситуация — не система; принципам и правилам не приписывать действие; в одном перечислении один род (замечание пилота 15.11.2026).

> **CAT-принцип (Computerized Adaptive Testing):** начало — со **среднего уровня (ст. 3)**, не с ст. 1. Опытных нельзя «сажать в первый класс» — это создаёт трение и не даёт информации. При оценке ≥ 3 → Фаза 2 пропускается; при оценке ≤ 2 → уточнение bottleneck (Фаза 2).
>
> **Два режима:** платформенный (DP.ROLE.042, WP-318) — ответы структурированные (chip/radio 1-5); коучинговый (человек-тренер) — открытые вопросы.

**Фаза 1. Первичный срез** (шесть вопросов: пять обязательных срезов и `cp.iwe`)

| cp-срез | Якорный вопрос (ст. 3-ориентир) | Рубрика 1-5 |
|---------|--------------------------------|-------------|
| **cp.rhy** | «Насколько регулярно вы выделяете время на саморазвитие и сохраняете результат?» | 1: занимаюсь случайно; 2: возвращаюсь время от времени, без расписания; 3: занимаюсь каждую неделю и отмечаю затраченное время; 4: занимаюсь в большинство дней и регулярно подвожу итоги; 5: устойчиво занимаюсь почти ежедневно, сохраняю результаты и могу помочь другому выстроить такой ритм |

| **cp.int** | «Как вы разбираете сложную ситуацию, когда в ней участвуют несколько людей или систем?» | 1: пока не использую специальный способ; 2: знаю отдельные понятия, но не применяю; 3: выделяю участников, их роли и границы; 4: строю связный разбор целей, ограничений и взаимодействий; 5: оформляю такие разборы в модели и помогаю другим ими пользоваться |
| **cp.agt** | «Какая доля ваших задач за последний месяц начата по вашей инициативе?» | 1: почти всё поручено другими; 2: иногда начинаю сам(а), редко; 3: около половины — мои; 4: большинство — моя инициатива; 5: определяю, чем занимаются другие |

Рабочие тексты вопросов в боте и скилле `/diagnose` — простым языком по этим рубрикам (РП-385 Ф18.12); при правке вопроса меняются оба места.

Если все 4 оценки ≥ 3 → Фаза 2 пропускается.

`cp.skl` оценивается отдельным вопросом: ритм и мастерство могут коррелировать, но один срез не выводится из другого. `cp.agt` запрашивается у всех (решение 20.10.2026); `bh.agn` остаётся независимым поведенческим сигналом.

**Фаза 3. Сверка независимых bh-сигналов** (0 вопросов, автоматически — платформенный режим)

Диагност запрашивает bh-данные из Аттестатора (DP.ROLE.041). `bh.*` не переписывает `cp.*` и не подставляется вместо ответа: совпадение повышает уверенность, расхождение запускает уточняющий вопрос или аудит артефакта. До устранения существенного расхождения оценка остаётся `indeterminate`, а не автоматически повышается.

| bh-сигнал | С чем сверяется | Правило |
|-----------|-----------------|---------|
| `bh.inv` | `cp.rhy` + `cp.skl` | Время — повод проверить ритм и освоение метода, но не доказательство их уровня |
| `bh.sys` + `bh.stb` | `cp.rhy` | Частота и разрывы подтверждают либо опровергают рассказ о ритме |
| `bh.awr` | `cp.wld` + `cp.int` | События рефлексии дают свидетельства для уточнения глубины |
| `bh.agn` | `cp.agt` | Два независимых измерения агентности; равенство кодов и автоматическое копирование запрещены |

> **Альтернатива для коучинга (без Activity Hub):** артефактный аудит даёт свидетельства для оценки уверенности: Git-репо, записи week-close/day-close, анализ речи, WP-контексты. Он не создаёт `cp.*` автоматически и не заменяет диагностический вопрос.

**Таблица допуска «ступень → этап программы»** (README практикумов «Личное развитие», раздел «Чек-лист защиты»; РП-385 Ф18.2, 15.11.2026). Расчёт ступени и допуск к этапу — разные решения: таблица только переводит уже посчитанную ступень в этап.

| Ступень | Этап программы | Переход, который этап готовит |
|---|---|---|
| 1 Случайный | S0 «Ритмичность» (с первой ступени допустим и S1) | 1 → 2 |
| 2 Практикующий | S1 «Собранность» | 1–2 → 3 |
| 3 Систематический | S2 «Агентность» | 3 → 4 |
| 4 Дисциплинированный | S3 «Системность» или сразу программа «Рабочее развитие» — выбор после консультации в IWE или у наставника (решение пилота 15.11.2026) | 4 → 5 |
| 5 Проактивный | программа «Рабочее развитие» | — |

Прежняя формула «ступень N → поток S N» вела в несуществующий этап S4 и сдвигала участника на этап вперёд; отменена.

**Квалификация «Работник» и выше** (решение пилота 15.11.2026, РП-385 Ф18). Ступени 1–5 и этапы S0–S3 относятся только к роли Ученика (PD.FORM.105 §2), поэтому при квалификации от «Работника» результат диагностики даёт два отдельных ответа:

1. **Программа по квалификации** — из квалификации, не из диагностики (PD.FORM.105 §3, §5): Работник, Стратег, Специалист, Практик — «Рабочее развитие»; Мастер — «Исследовательское развитие» или следующий круг «Рабочего развития»; Реформатор — «Исследовательское развитие» или «Просветительская программа»; Деятель (революционер, в некоторых записях «Революционер» или «Общественный деятель») — «Просветительская программа».
2. **Роль Ученика** — что показала диагностика: все пятёрки (или подтверждённая ступень 5) — пробелов нет, дополнительно проходить ничего не нужно; ступень 4 — можно также пройти S3, нужно ли — консультация в IWE или у наставника; ступени 1–3 — ступень, самый слабый срез и этап «Личного развития» по таблице выше как дополнительная рекомендация.

Квалифицированному человеку прямо говорится, что диагностика измеряет роль Ученика — умение развивать себя и свою ИИ-среду — и квалификацию не меняет и не подтверждает. Пометка о признаках пятой ступени ему не показывается. Нет данных о квалификации — результат как у Ученика.

Этот блок определяет размещение внутри базовых потоков ЛР. Ступень 5 впервые подтверждается только полным gate §5.2 и может быть достигнута в продвинутой траектории ЛР; при свежем полном gate действует `rr_readiness_status = ready`, а передача и старт РР оформляются отдельно. Один cp-профиль не может выдать ступень 5 в обход остальных условий.

**TTL:** `valid_until = assessed_at + 6 months` для всех пяти обязательных срезов (четыре стержневых + `cp.agt`) при любой текущей оценке (с 20.10.2026; прежде `cp.agt` — только на переходе 4→5). Просроченный стержневой профиль даёт `stage_evaluation_status = indeterminate`, а не понижает `attained_stage`.

**Параметры переоценки (v5.1):**
- Минимальный интервал между повторными диагностиками: **7 дней** (ранее 30 дней в diagnose-iwe v4.x). Если профиль моложе 7 дней — показать текущий результат и предложить вернуться к диагностике после истечения интервала; не запускать её принудительно. В пользовательском тексте использовать объяснение из границы выше, не слово «кулдаун».
- Для ст.4+: `bottleneck_slice = None`. Все пять обязательных срезов (включая `cp.agt`) ≥ 4 — разрыв между ними незначителен, bottleneck-концепция ступеней 1–4 теряет операциональный смысл. Отдельного transition blocker по `cp.agt` больше нет: агентность входит в общий минимум (решение пилота 20.10.2026). Старое имя runtime-поля `bottleneck_slot` требует отдельной миграции адаптера.
- Полный TTL профиля: 6 месяцев — без изменений.

*Источник изменений: WP-370 + commit 3a173605 FMT-exocortex-template 2026-06-18.*

Использует bottleneck для квартального фокуса: цель = поднять baseline cp-bottleneck на +1 индекс.

### 6.3 Портной (MIM.SOP.001)

- Фокус-контент (квартал) = bottleneck одного из четырёх стержневых cp-срезов: cp.rhy, cp.wld, cp.skl, cp.int
- При подготовке 4→5 `cp.agt < 4` даёт отдельную рекомендацию по агентности, не меняя bottleneck и не понижая ступень 4
- cp.auto определяет канал доставки (глубина автопилота → тип контента)
- cp.int: ст. 3→4 расширение потенциала через M4 в ЛР; 4→5 — продолжение в продвинутой траектории ЛР с формированием готовности к РР

**Стадия мастерства IWE — функция ступени Ученика (не cp-индекса).** Source-of-truth:

| Ступень Ученика | Имя стадии мастерства IWE | Ожидаемый cp.iwe | Ожидаемый cp.cre |
|---|---|:---:|:---:|
| 1 Случайный | **Пользователь-1** | 1 | 0 |
| 2 Практикующий | **Пользователь-2** | 2 | 0 |
| 3 Систематический | **Пользователь-3 + Разработчик-1** (одновременно, переход) | 3 | 1 |
| 4 Дисциплинированный | **Разработчик-2** | 3+ (поддерживается) | 2 |
| 5 Проактивный | **Разработчик-3** | 3+ (передаётся другим) | 3 |

**Принцип лестницы:** на ст.1-2 человек осваивает пользование средой (ось управления — ведущая). На ст.3 — точка качественного перехода: одновременно достигает Пользователь-3 и начинает Разработчик-1. На ст.4-5 ведущая ось — создание (Разработчик-2 → Разработчик-3); пользование удерживается на уровне 3+ как фон.

**Что показывает Портной в персональном руководстве** (блок «Стадия мастерства IWE»):
- Имя текущей стадии (по ступени Ученика — из таблицы выше).
- Фактические cp.iwe и cp.cre (что измерил Диагност).
- Дельта от ожидания: если cp.iwe или cp.cre ниже ожидаемого → подсветить «что подтянуть».

**Логика рекомендаций Портного:**

1. Если фактический cp.iwe ниже ожидаемого для ступени → контент по освоению ритуалов (Day Open/Close, Week Close, маршрутизация).
2. Если cp.cre = 0 на ст.3+ → контент по начальной кастомизации среды (settings, первые Pack-разделы, extension-файлы) как вход в роль Разработчика-1.
3. Если cp.cre ниже ожидаемого на ст.4-5 → контент по углублению создания (Pack-домены, MCP-инструменты, расширения).
4. Если профиль соответствует или опережает ожидание → контент следующей стадии или фундаментальное расширение (cp.wld, cp.int).

**cp.iwe и cp.cre не блокируют ступень Ученика** — это рекомендательные оси. Ступени 1–4 определяются двойным RCS-gate (§5.1); ступень 5 дополнительно требует полного gate Проактивного (§5.2), независимо от того, началось ли РР.

## 8. Ограничения текущей версии (known gaps)

1. **Калибровка cp-рубрик.** Рубрики baseline-индексов требуют валидации на пилоте — особенно границы idx 3↔4 и 4↔5. Статус: **ожидает v5** (пилоты, лето 2026).
2. **cp.knw (Системное знание).** Рубрики — минимальная домен-независимая версия. Домен-специфичные рубрики (KW, UX, Engineer) — в **v5**, после проектирования программы «Рабочее развитие».
3. **cp.agt измерение.** Поле `initiator` в `wp_created` отсутствует (WP-214 Ф10.5). MVP: все wp_created = самоинициированные. После WP-214: только `initiator=user`.
4. **bh.scl без данных actual_hours.** Поле реального времени по wp_completed появится после доработки Activity Hub. До тех пор bh.scl использует фиксированный вес из iwe-actions-catalog.md.
5. **TTL cp-срезов не реализован автоматически.** Диагност обязан вручную проверять дату последнего диагноза. Автоматический TTL-триггер — WP-310 Ф5+.
6. **cp.auto / cp.exo сложно разделить.** В реальном диагностическом диалоге граница автопилота и экзоскелета размыта. MVP: вопрос «можешь объяснить без "ИИ подсказал"?» как разделитель.
7. **Downstream-вычислители не мигрированы на v5.0.1.** Действующий код всё ещё использует прежние правила cp-подтверждения и маршрутизации. Миграция должна отдельно покрыть: `current_stage = NULL` до полного недельного bh-окна и свежего core-cp; источник дней практики `activity_domain` с исключением ритуальных маркеров; tri-state `form093_real_change_gate_status`; nullable `attained_stage` до первого подтверждения. До отдельной миграции и проверки потребителей эта версия является нормативной draft-формализацией: автоматическое присвоение ступени и готовности к РР по новому gate не заявляется внедрённым.

## 12. MVP: Автоматический расчёт ступени (bh-характеристики, WP-310)

> **Статус:** v4, май 2026 (WP-310 Ф1-Ф9). 7 bh-характеристик из событий Activity Hub — автоматический сигнал Аттестатора. Он не заменяет Диагноста и не создаёт cp-значения; итог ступеней 1–4 всегда требует композиции §5.1.
>
> **Кодирование:** `bh.` = behaviour (поведенческие метрики из событий). `cp.` = capacity (потенциал через рубрики Диагноста). Старые коды S/T/M/W/A → bh.sys/bh.inv/bh.met/bh.awr/bh.agn.
>
> **Весовая конфигурация:** `DS-ecosystem-development/…/Data-Governance/iwe-actions-catalog.md §7`.

### 12.1 Модель 7 bh-характеристик

| Код | Характеристика | Ось | Тип | Показатель |
|-----|----------------|-----|-----|------------|
| **bh.sys** | Систематичность | Мастерство | обязательная | `self_dev_days_per_week` — среднее дн/нед в скользящем окне |
| **bh.inv** | Инвестиционность времени | Мастерство | обязательная | `avg_hours_per_week` — среднее ч/нед (slot_logged + lesson_completed) |
| **bh.met** | Методичность | Мастерство | компенсаторная | `methodical_events_per_month` — применение методов, событий/мес |
| **bh.awr** | Осведомлённость | Мировоззрение | основная | `worldview_score` — взвешенная сумма событий рефлексии за 30 дней |
| **bh.agn** | Агентность | Мировоззрение | основная | `agency_score` — взвешенная сумма самоинициированных событий |
| **bh.scl** | Масштабность | Мастерство | информационная | `scale_score` — РП с фактическим временем (wp_completed × actual_hours) |
| **bh.stb** | Устойчивость | Мастерство | gate | `max_gap_days` — максимальный разрыв без подтверждённого `practice_day` |

> **Различение типов.** «Обязательная» = ноль блокирует ступень. «Компенсаторная» = низкое не блокирует при компенсации. «Основная» = наибольший вес в оси Мировоззрения. «Gate» = срабатывает как дополнительный порог при расчёте ступени.

### 12.2 Показатели и рубрики

#### bh.sys — Систематичность

**Смысл:** регулярность именно саморазвития. `git_commit`, `wp_created`, `coding_time` — рабочая активность, не считается.

**Принцип окна:** растёт со ступенью. Проактивный оценивается за 24 нед — нужно доказать устойчивость на дистанции.

**Множество содержательных событий `SELF_DEV_EVENT_TYPES`** (полный реестр в `iwe-actions-catalog.md §0`):
```
lesson_completed, knowledge_extracted, pack_updated, qualification_granted,
strategy_session_completed, iwe_session
```

Это множество применяется для семантической классификации событий, но **не является источником дней практики**. `day_plan_opened`/`day_open`, `day_plan_closed`/`day_close`, `week_plan_closed` и `month_plan_closed` — ритуальные маркеры входа/закрытия; они явно не входят в `SELF_DEV_EVENT_TYPES` и сами по себе не создают день практики.

**Единственный источник `practice_day` для `bh.sys` и `bh.stb`:** подтверждённое событие `learning.domain_event` с `activity_domain IN ('practice', 'learning')`, причём `event_type NOT IN RITUAL_MARKER_EVENT_TYPES`. День считается один раз по календарной дате независимо от числа событий. Это реализует D.146 и согласовано с Event Model PD.FORM.095: маркер может сопровождать практику, но не заменяет её.

| Индекс | Ступень-аналог | Порог дн/нед | Окно |
|--------|:---:|:---:|:---:|
| **0** | — | < 1 | — |
| **1** | Случайный | ≥ 1 | 1 нед |
| **2** | Практикующий | ≥ 3 | 4 нед |
| **3** | Систематический | ≥ 5 | 8 нед |
| **4** | Дисциплинированный | ≥ 6 | 12 нед |
| **5** | Проактивный | ≥ 6.7 | 24 нед |

> **6.7 дн/нед = 1 день пропуска в месяц.** Достижимо для Проактивного с ежедневной практикой.

#### bh.inv — Инвестиционность времени

**Источники (К4 fix):** только `slot_logged.hours` + `lesson_completed.duration_minutes/60`.

> **К4 (WP-310):** `coding_time` (WakaTime) исключён — он включает все репозитории, в том числе рабочие. Используются только чистые учебные события. Нормативы установлены с учётом занижения этих источников.

**К4-uplift (Ф13, 15 мая):** `slot_logged` принимает `payload.source` ∈:
- `active` — вручную через `/slot N` после реальной практики
- `self_report_backfill` — одноразовый onboarding-ввод среднего времени за прошлый период
- `self_report_daily` — ответ на Day Close prompt (если slot за день = 0)
- `self_report_weekly` — ответ на Week Close prompt (catch-all)

Все четыре источника равноценны для bh.inv. `coding_time` остаётся исключённым — он мерит ВСЕ репо, не декларирует учёбу. Self-report допустим, потому что декларация явна и осознанна.

**bh.sys и bh.stb НЕ ВКЛЮЧАЮТ self_reported события или ритуальные маркеры.** Только подтверждённая доменная активность по правилу `practice_day` выше. Self-report подтверждает ВРЕМЯ, не регулярность — иначе мы инфлируем оба показателя из одного ввода.

**Правка истории:** UPDATE `payload.hours` существующего события (overwrite, MVP). Корректирующие события (immutable event log) — backlog при необходимости audit-trail.

| Индекс | Ступень-аналог | Порог ч/нед | Окно |
|--------|:---:|:---:|:---:|
| **0** | — | < 0.5 | — |
| **1** | Случайный | ≥ 0.5 | 1 нед |
| **2** | Практикующий | ≥ 4 | 4 нед |
| **3** | Систематический | ≥ 6 | 8 нед |
| **4** | Дисциплинированный | ≥ 10 | 12 нед |
| **5** | Проактивный | ≥ 10 | 24 нед |

#### bh.met — Методичность

**Показатель:** `COUNT(events за 30 дней)` из: `lesson_completed`, `knowledge_extracted`, `pack_updated`, `qualification_granted`.

| Индекс | Диапазон |
|--------|----------|
| **0** | 0 |
| **1** | 1–3/мес |
| **2** | 4–10/мес |
| **3** | 11–25/мес |
| **4** | 26–50/мес |
| **5** | > 50/мес |

#### bh.awr — Осведомлённость (worldview score)

**Окно:** 30 дней (З4, WP-310 — явно зафиксировано в `AWR_WINDOW_DAYS = 30`).

**Показатель:** взвешенная сумма событий рефлексии за 30 дней → индекс 0–5. Веса: `iwe-actions-catalog.md §7`.

| Индекс | Операционные признаки |
|--------|----------------------|
| **0** | Рефлексий нет |
| **1** | Единичные рефлексии |
| **2** | Начинает видеть паттерны. Системный язык — эпизодически |
| **3** | Регулярные рефлексии (Week Close / Month Close). Различает роли, методы |
| **4** | Чёткий системный язык. Видит себя как деятеля в системах |
| **5** | Формирует системное видение у других |

#### bh.agn — Агентность

**Показатель:** взвешенная сумма за 30 дней → индекс 0–5. Веса: `iwe-actions-catalog.md §7`.

| Индекс | Операционные признаки |
|--------|----------------------|
| **0** | Нет инициированных действий |
| **1** | 1–2 самоинициированных действия/мес |
| **2** | Несколько, есть хотя бы 1 самостоятельный РП |
| **3** | ~50% задач из собственных целей. 1–2 активных РП |
| **4** | Несколько независимых РП. Действует в неопределённости |
| **5** | Формирует повестку для ближнего круга |

**Расхождение с §13.1.2 (21.11.2026, РП-576 Ф6.1).** Признака инициатора в событиях нет (§12.5 п.1: все `wp_created` считаются самоинициированными), поэтому рубрика не подтверждает ни инициативу, ни долю решения человека: действующий индекс мерит объём событий РП и стратегирования. Уровень 5 — охват (§13.1, общие правила п.3). Рубрика сохраняется до замены по паспорту шкал (РП-151, Часть 6) — после признака инициатора (РП-427) и калибровки (РП-493).

#### bh.scl — Масштабность

**Показатель:** `SUM(actual_hours по wp_completed за 30 дней)` → взвешенная сумма → индекс 0–5.

> **К2 fix (WP-310):** bh.scl должен мерить фактически отработанное время по РП (actual_hours из payload wp_completed), а не бюджет заявленный при создании. Без поля `actual_hours` в событии — используется фиксированный вес, что является приближением. Тикет на добавление поля: WP-214 Ф11.

**Информационная характеристика** — не блокирует ступень в текущем MVP. Используется Навигатором для оценки «масштабности деятельности» учеников на ст.3+.

#### bh.stb — Устойчивость

**Показатель:** максимальный разрыв без подтверждённого `practice_day` (в днях) за учётный период ступени.

> **bh.stb ≠ bh.sys.** bh.sys = средняя частота (сколько дней из семи). bh.stb = худший разрыв (самый длинный простой). Оба нужны: высокое bh.sys с одним разрывом-3-недели = высокая bh.sys, но низкое bh.stb.

**Нормализация bh.stb:**

| bh.stb индекс | Макс. разрыв | Ступень-аналог |
|:---:|:---:|:---:|
| **5** | ≤ 1 день | Проактивный |
| **4** | 2–3 дня | Дисциплинированный |
| **3** | 4–7 дней | Систематический |
| **2** | 8–14 дней | Практикующий |
| **1** | 15–30 дней | Случайный |
| **0** | > 30 дней | — |

**STB_GATE** (минимальный bh.stb для получения ступени): ст.2 ≥ 1, ст.3 ≥ 2, ст.4 ≥ 3, ст.5 ≥ 4.

**Легенда статусов.** «В составе профиля» — ровно пять личностных характеристик (решение пилота 15.10.2026); «гейтит» — входит в минимум ступени.

**Уточнение вокабуляра (найдено независимой проверкой 14.09, обновлено 31.10.2026).** «В составе профиля», «гейтит» и «вспомогательная» — статусы ЭТОЙ модели по участию в расчёте ступени (§13.3), своя ось; «гейтит» в колонке «Статус в боевом расчёте» значит «входит в минимум ступени» и не переиспользует термин «gate» из `PD.FORM.093` (там — составное условие перехода к ступени 5, §5.4 того документа; уточнено 21.11.2026 по решению пилота 20.11, п.3: это условие ступени 5, к степени квалификации не относится, значения порога — калибровка РП-493). Ясность `PD.FORM.093` называет gate, а в этой модели она в составе, но пока не гейтит (мост ясности, решение 15.10.2026): статусы не смешаны в одной колонке.

**Омонимия «Оснащённость».** Ось состояния платформы `belonging` (тир T0-T4) называется тем же словом — другая сущность (что система знает о пользователе), не характеристика. Пилот 13.09 отклонил переименование характеристики (слово уже прозвучало перед живой когортой практикума «Собранность», установочная встреча 13.09) — сущности разводятся контекстом употребления, не именем.

**Структура измерения (по FORM.088 §2, «квартет»).** Каждая характеристика — и v5-каталога, и этого раздела v6 — измеряется четвёркой: характеристика / показатель / значение (сейчас + baseline) / потенциал (лучшее показанное значение с условиями показа). Элементы «характеристика/показатель/значение» сохраняются без изменений (см. §13.2); элемент «потенциал» определён решением пилота 20.11.2026, п.13 (`PD.FORM.088` §2): ведётся по носителю, результат пары человеку не переносится без выделенной доли его решения; способ записи по каждой характеристике — §13.7 п.2.

**Общие правила измерения (решения пилота 17.11 и 20.11.2026; записано 21.11, РП-576 Ф6).** Действуют для всех характеристик каталога; у характеристик — только ссылки и своя специфика.
1. **Носитель.** Носитель ступени ученика — человек (решение пилота 20.11: «он такой даже без инструментов»). Признак относится к носителю по трём вопросам (критерий принят пилотом 20.11): убрали ИИ-среду на срок окна шкалы — признак сохраняется → человек; оставили среду, заменили человека — сохраняется → признак ИИ-среды (в каталоге его учитывает оснащённость пары «человек + ИИ-среда», §13.1.5); исчезает в обоих случаях → признак пары «человек + ИИ-среда». Программа развития строит железного человека (пару «человек + ИИ-среда», `PD.FORM.001`), а ступень фиксирует рост человека в роли ученика; лестница железного человека — отдельная заготовка (стадии мастерства IWE, §6.3). Событие в IWE по умолчанию — след пары; человеку засчитывается доля его решения; долю не выделить — свидетельство записывается на пару, у человека «нет данных», не ноль. Уточнение паспорта шкал РП-151 (Части 6 и 10, после независимой проверки 20.11): предложение агента, принятое без изменений, — тоже «нет данных» о доле человека. Одно свидетельство дважды не засчитывается: один и тот же признак не назначается двум характеристикам, а разные признаки одного эпизода (кто выбрал направление, на каком основании) могут относиться к разным.
2. **«Нет данных» ≠ низкое значение.** Ноль событий за 30 дней — «нет данных»; при «нет данных» у человека остаётся прежняя ступень (решение пилота 17.11.2026).
3. **Охват ≠ уровень (модель шкалы, решение пилота 17.11).** Масштаб адресатов действия или передачи (для себя, ближний круг, сообщество, общество) — координата охвата. Признаки старых рубрик, описывающие только масштаб адресатов («формирует повестку для ближнего круга», «определяю, чем занимаются другие»), уровень характеристики не задают; сам факт передачи метода может быть свидетельством владения им.
4. **Пак и паспорт шкал.** Пак держит определения, аспекты, границы, носителя и честный статус источника. Уровни 0–5, пороги и порядок разметки — паспорт шкал РП-151 (`DS-my-strategy/inbox/WP-151/scale-passport-draft.md`), калибровка — РП-493, расчёт — РП-602. Старые рубрики (`cp.*`, `bh.*`, карточки `PD.FORM.093`) сохраняются до замены по паспорту шкал; расхождения с определениями отмечены у самих рубрик. Где в пометке написано «решение пилота», это решение; уточнения из паспорта шкал и его независимой проверки подписаны ссылкой на паспорт.

**Состав профиля и вспомогательные характеристики.** Не все характеристики каталога учитываются в расчёте ступени (§13.3) одинаково; любознательность в нём не учитывается совсем (§13.1.7). **В составе профиля (решение пилота 15.10.2026):** собранность, агентность, зрелость, системность, ясность — пять личностных. **Гейтят** ступень (участвуют в `min_личн`/`v2`) четыре из них; ясность в составе, но не гейтит, пока мост ясности даёт минимум всем. Оснащённость (средовая) в каталоге; в состав войдёт на этапе 2 после появления источника (§13.2). **Вспомогательные:** продуктивность, ресурсность, стрессоустойчивость — читаются той же единой точкой чтения, что и характеристики состава (контракт «витрины», §13.7 п.4), отслеживаются наравне с остальными, но **не входят в расчёт `stage_v6`** и не блокируют его через `dormant-no-source`. Это прямое следствие того, что две из трёх (ресурсность, стрессоустойчивость) сегодня без источника (§13.2) — при обратном решении («все девять обязательны») формула была бы невычислима постоянно, что и было бы честной причиной её не вводить вовсе.

**Состав по этапам (решение пилота 15.10.2026).** Действующий стартовый состав (в решении 15.10 он назван составом «обязательных» характеристик; слово здесь цитата) — пять личностных с источниками: собранность, агентность, ясность, зрелость, системность. Оснащённость входит в состав после появления источника (§13.2). Каждое изменение состава проверяется отдельным теневым прогоном рядом с действующим расчётом: добавление характеристики способно понизить ступень (пример: [3,4,4,4,4] → 4; с оснащённостью 1 → [1,3,4,4,4,4] → 3).

#### 13.1.1 Аспекты собранности

> **Уточнение 17.11.2026 (решения пилота, РП-151 Ф27; гипотеза до калибровки — PD.FORM.145).** Ряд «в работе / во времени / в результате» смешивает два основания: масштаб (одна работа или ряд работ) и момент работы. Целевая модель описывает собранность окнами (слот → день → неделя → месяц → квартал → год) с уровнем 0–5 в каждом окне; фазы «до — во время — после» относятся к слоту. Систематичность выделения слота на новое (сам факт, без объёма) и восстановление после перерывов остаются сторонами собранности (окна неделя и дольше); объём часов — отдельное условие §13.3а. Организация состояния собранностью не оценивается — это продуктивное состояние (PD.FORM.038). Аспекты ниже сохраняются как действующее описание до перехода расчёта.

- **В конкретной работе:** внимательность, концентрация, управляемость переключений, организация состояния и режима.
- **Во времени:** систематичность (обобщающий аспект воспроизводимости практики); регулярность, ритмичность, восстановление после перерывов — уточнения систематичности, не отдельные счётчики.
- **В результате** (новый аспект, добавлен 13.09): доведение до результата — закрывает начатое артефактом, не бросает на середине. Переиспользует те же поведенческие сигналы, что и остальные аспекты «во времени» (учёт и вклад времени, устойчивость практики), не заводит новый счётчик. **Обоснование границы — структурное, не техническое** (см. §13.1.6): этот аспект самостоятельно оправдан внутри модели ступени, независимо от состояния соседней характеристики другой лестницы. Операциональная оговорка о частичном пересечении сигналов со сломанной формулой другой лестницы — в §13.2, не здесь: здесь граница онтологическая, там — честность источника.

Границы: собранность ≠ агентность (агентность — вектор, собранность — удержание движения по вектору, Kimi раунд 1). Собранность ≠ оснащённость (мастерство использования средств vs их наличие).

#### 13.1.2 Аспекты агентности

Самостоятельность целеполагания, инициативность, автономность решений, ответственность за решения, коррекция направления, масштаб инициируемых изменений. Агентность ≠ «всё сам» — осмысленно принятая чужая цель и делегирование ИИ тоже агентность; критерий — кто принял решение и на каком основании.

**Доля решения (записано 21.11.2026, РП-576 Ф6.1).** Носитель агентности и правило доли решения — решения пилота 20.11 (§13.1, общие правила п.1). Что считается долей человека, по паспорту шкалы агентности (РП-151, Часть 6, после независимой проверки 20.11): своя постановка задачи или направления; поправка или дополнение предложения агента; осознанно принятая чужая цель или поручение ИИ с названным основанием. Низкое значение ставится только при открытом выборе — когда агент не предлагает направление, а спрашивает (там же; частоту открытого выбора решил пилот 20.11). Аспекты «инициативность» и «ответственность за решения» действующими источниками отдельно не подтверждаются; событийный заменитель им не назначается. Уровни, пороги и порядок разметки — паспорт шкалы агентности (РП-151, `scale-passport-draft.md`, Часть 6), калибровка — РП-493.

**Четыре разных объекта (исправлено 21.11.2026; консолидация 13.09 ошибочно назвала первые три одним объектом).** (1) Характеристика «агентность» — эта строка каталога и `CHR.K.001`. (2) Срез `cp.agt` — действующий диагностический срез, самооценка доли самоинициированных действий; долю решения не измеряет. (3) `agency_idx` профилировщика — составной индекс активности и регулярности (регулярность слотов, активность, обучение, реакция на уведомления, стаж), не агентность; учитывается в пороге профиля выпускника `PD.FORM.093` под именем агентности. (4) `bh.agn` — объём событий РП и стратегирования за 30 дней. Расхождение передано владельцу расчёта (РП-602): различать «нет данных» и низкое значение; судьба `agency_idx` (переименовать или вывести из порога выпускника) — его решение. Различать происхождение предложения и решение человека в событиях — потребность, переданная РП-427. `MIM.M.004` (шкала делегирования по степеням квалификации) — качественно другое (распределение ответственности во внешней квалификационной лестнице, не личная агентность), переименовано в «делегирование», в каталог не входит.

**Сверка с `PD.FORM.113` (21.11.2026; прежде — открытый пункт).** `PD.FORM.113` описывает широкое понятие (желание + возможность + ответственность, масштаб до человечества, кластер «Элита») и в расчёте не учитывается. Желание инициировать и ответственность — аспекты этой характеристики. «Возможность» (ресурсы, мастерство, контекст) — не агентность: средства относятся к оснащённости, остальное пересекается с другими характеристиками и сверяется владельцами их определений. Уровни масштаба (сообщество, общество, человечество) — координата охвата, не уровень агентности. Различение «агентность ≠ активность» совпадает по слову, но в `PD.FORM.113` §2 отличие задано масштабом, который здесь относится к охвату; здесь отличие задано долей решения. Действующая гейтовая агентность (`cp.agt`, используется в `PD.FORM.108` — порог ≥4 на входе в «Рабочее развитие») — узкая версия.

#### 13.1.3 Аспекты мировоззренческой зрелости

Осмысленность убеждений, обоснованность, согласованность, готовность пересматривать при новых свидетельствах, связь представлений с деятельностью, рефлексия пути. Количество событий рефлексии зрелость не присваивает; источники — диагностика (для сверки) и следы бесед (решение пилота 20.11, ниже).

**Что мерит шкала (уточнено 21.11.2026, РП-576 Ф6.2; по паспорту шкал РП-151, Часть 7, после независимой проверки 20.11; источник — решение пилота 20.11).** Качество оснований решений, а не содержание картины мира. Действующий срез `cp.wld` мерит фазу мировоззренческой дуги (`PD.FORM.080` §3), а фазы дуги привязаны к ступеням — подавать фазу дуги как зрелость значит выводить ступень из самой ступени. Источником зрелости служат следы бесед: решения человека с названными им основаниями; разметка — по порядку паспорта шкал РП-151 (Часть 7, раздел 7.7: выгрузка программой, независимая разметка вслепую, наставник на выборке, ежемесячная проба без агента). Готовое основание агента — по §13.1, общие правила п.1.

Границы: агентность — кто решил и сменил ли направление; зрелость — качество названного основания и его пересмотра; системность — через какое описание объекта решает. Один эпизод не засчитывается дважды как событие.

#### 13.1.4 Аспекты системности

Владение системными различениями, построение моделей, работа со связями и уровнями, учёт динамики и последствий. Центральный аспект — применение системного описания к решению (обосновал выбор, назвал влияние и ограничения, проверил последствия), не наличие разбора самого по себе.

#### 13.1.5 Аспекты оснащённости

Функциональное покрытие, информационная оснащённость, связанность средств, доступность и надёжность, управляемость. Реляционная характеристика «исполнитель-среда» — свойство условий, не внутренняя способность.

Граница с агентностью/системностью: наличие/пригодность/работоспособность средств → оснащённость; умение создавать средства и управлять средой → агентность/системность; мастерство использования среды в работе → собранность.

Граница с ресурсностью (§13.1.6): оснащённость = наличие нужных средств (пассивное состояние); ресурсность = умение их мобилизовать (активное качество).

**Шкала оснащённости (решение пилота 15.10.2026).**

| Балл | Признак |
|---|---|
| 1 | собственной рабочей среды нет: только бот или браузер |
| 2 | среда частичная: помощник в браузере или подключённый цифровой двойник, собственного репозитория нет |
| 3 | основные функции работы покрыты средствами собственной среды: планирование и учёт, знания и память, ИИ-помощник; открытие и закрытие дня (или их аналог) работают. Пример: установлен шаблон IWE, есть браузерная версия ИИ-среды |
| 4 | всё из балла 3; средства связаны (данные переходят между ними без ручного переноса), среда надёжна — без критических сбоев за месяц, обновляется; налажено не меньше 50% методов каталога стиля жизни и работы (LMS.M, `WP-600`), у которых есть средство в среде. Пример: актуальная версия шаблона IWE, проверка установки без критических пропусков |
| 5 | всё из балла 4; налажено не меньше 80% таких методов; среда допускает настройку правил, ролей агентов и памяти, настройки применяются и сохраняются |

Баллы 3–5 описаны через функции среды (аспекты выше: покрытие, связанность, надёжность, управляемость), шаблон IWE — пример, а не условие; чужая среда с теми же функциями оценивается так же (решение пилота 20.11.2026, п.19; формулировка 21.11, РП-576; каталог методов — РП-600). Носитель оснащённости — пара «человек + ИИ-среда» (железный человек, §13.1, общие правила п.1). Учитывается метод, который налажен и работает в среде, а не частота его применения: частота относится к собранности (граница выше: мастерство использования среды → собранность). Тир аккаунта T0-T4 источником не является (омоним, §13.1).

#### 13.1.6 Ясность, продуктивность, ресурсность, стрессоустойчивость

Импортированы из `PD.FORM.093` (§3.2 «Карточки 8 характеристик» — ясность карточка 1, продуктивность/ресурсность/стрессоустойчивость карточки 6-8; решение пилота 13.09) как отдельные характеристики каталога, не сливаются с существующими (в частности ясность отдельна от зрелости/системности — про сведение обоих в конкретный результат прямо сейчас, не про основания или инструмент по отдельности). Ссылка «§2.6-2.9» в более ранних записях этого решения (карточка `WP-576`) относится к нумерации концепт-документа сессии, не к самому `PD.FORM.093` — уточнено независимой проверкой 14.09.

Ясность — gate-характеристика перехода 4→5 в `PD.FORM.093` (сводная таблица §3.1, composition rule §5.4; baseline ≥4). Продуктивность/ресурсность/стрессоустойчивость — supporting (baseline-ориентир ≥3, просадка не блокирует переход, требует индивидуального плана).

**«Способность производить» — не входит в этот каталог (структурная граница, не техническая).** `PD.FORM.093` определяет отдельную gate-характеристику «способность производить» (доводит ли работу до артефакта вообще — бинарный оттенок 0-5 по числу доведённых работ; ось «есть/нет результата»). Продуктивность — другая ось, «сколько ценности за час» — они измеряются не на одном интервале и не сравниваются напрямую. «Способность производить» гейтит степень квалификации (внешнюю лестницу, §13.4), не ступень RCS этого документа. **Решение (уточнено раундом критики 13.09): она не входит в каталог ступени ПОТОМУ, ЧТО принадлежит другой лестнице — не потому, что её формула сегодня сломана.** Факт «`production_capacity_idx` в проде всегда 0 (баг коллектора, передан в WP-7)» — это диагноз кода, не онтологическое основание; если баг починят, характеристика останется характеристикой степени квалификации, а не переедет в этот каталог автоматически.

Отдельно от этого решения — аспект «в результате» собранности (§13.1.1) **самостоятельно обоснован внутри модели ступени**: доведение начатого до артефакта — законная грань собранности как таковой. То, что его сигналы (`bh.inv`, `bh.met`) частично совпадают с сигналами сломанной формулы «способности производить», не делает один аспектом другого — это два независимых обоснования, которые опираются на пересекающиеся, но не тождественные данные, что допустимо между разными лестницами.

#### 13.1.7 Любознательность (решение пилота 20.11.2026; внесено 21.11, РП-576 Ф6.6)

Опора в паке — маркер «Любопытство как фон» (`PD.FORM.099`). Носитель — человек; для пары «человек + ИИ-среда» — «не применимо», пока не определена отдельная мера. Характеристика в каталоге, в расчёте ступени не учитывается (решение пилота 20.11). В профиле выпускника `PD.FORM.093` не учитывается (решение пилота 21.11.2026: профиль выпускника остаётся из восьми характеристик; предложение передачи РП-151, паспорт шкал 11.6 п.1, «восемь → девять» отклонено). Границы: зрелость и системность — качество понимания и оснований, здесь — тяга к пониманию; срыв взятой работы ради нового интереса и «любопытство как избегание» — собранность; решение создать РП — агентность; интерес в моменте — состояние, характеристика — обычный уровень за 4–8 недель; вопросы, целиком рождённые расписанием или упражнением, не считаются. Единица разметки, уровни и кандидаты источников — паспорт шкал РП-151 (Часть 11), пороги и источник — РП-493.

### 13.3 Ступень: согласованный профиль

> **АрхГейт обязателен перед первым кодом**, реализующим это правило (стейдж-эвалюатор, матрица минимумов §12.3 v5) — смена алгоритма присвоения ступени системного уровня. Правка Pack-формализации ниже гейта не требует. **АрхГейт пройден 14.10.2026; с 15.10.2026 правило действует в боевом расчёте** (`activity_hub/core/stage_v6.py::derive_stage_v6`, вызывается из `stage_evaluator`, РП-602). Стартовый состав обязательных — по решениям пилота 15.10 (РП-602 Ф2-Ф3). Приёмка владельцем модели (РП-576, 20.10.2026): §5.1 соблюдён; cp-часть §5.2 — в строгой редакции выше; составные части §5.2 (ii) метрический gate и (iii) подтверждение охвата изменений в коде не реализованы — блокер допуска к переходу 4→5 до первого кандидата (РП-602).

**Формула.** Профиль — вектор оценок характеристик состава (§13.1, целые 1-5). Свёртка в ступень — формула ниже по тем из них, что гейтят (сегодня четыре: собранность, агентность, зрелость, системность; ясность в составе, но не гейтит). Вспомогательные (продуктивность, ресурсность, стрессоустойчивость) в формулу не входят — видны отдельно на витрине (§13.7 п.4). Отсортировать оценки гейтящих по возрастанию: v1≤v2≤…≤vn (n=4 сегодня, меняется вместе с составом). `min_личн` = минимум среди гейтящих личностных характеристик. Оснащённость сегодня не входит ни в ряд v1..vn, ни в `min_личн` (в каталоге; этап 2, источника нет, РП-602 Ф6); правило её участия после появления источника этой правкой не меняется. Порядок присвоения ступени (два пути, ступень 5) — §5.1; решено 31.10, в код не влито.

```
stage_v6 = min( v2 , min_личн + 1 )
```

Формула определена одинаково при любом составе гейтящих характеристик — не фиксирует конкретное число n, но её ЗНАЧЕНИЕ зависит от состава (вторая по возрастанию оценка `v2` и `min_личн` меняются при добавлении/удалении гейтящей характеристики). Тотальна (определена для любого профиля из ≥2 гейтящих характеристик), монотонна (не убывает при росте любой оценки). Крайний случай `n < 2` гейтящих характеристик (если состав когда-нибудь сократится) формулой не покрыт — отдельное решение при таком сокращении состава, не покрывается этой версией.

Примеры (четыре гейтящих; ясность в составе, но на результат не влияет; примеры с оснащённостью вернутся с этапом 2):
- собранность=3, агентность=3, зрелость=5, системность=5 → отсортировано [3,3,5,5] → `v2=3`, `min_личн+1=4` → **stage_v6=3**
- собранность=1, агентность=5, зрелость=5, системность=5 → [1,5,5,5] → `v2=5`, `min_личн+1=2` → **stage_v6=2**
- собранность=4, агентность=4, зрелость=4, системность=4 → [4,4,4,4] → `v2=4`, `min_личн+1=5` → **stage_v6=4**
- собранность=2, агентность=4, зрелость=4, системность=4 → [2,4,4,4] → `v2=4`, `min_личн+1=3` → **stage_v6=3**

**Гипотеза требования собранности по окнам (17.11.2026, PD.FORM.145 §5; не действует до калибровки).** Ступень 2 — уровень ≥3 в окне «слот», 3 — в окне «день», 4 — в окнах «неделя» и «месяц», 5 — в окне «квартал» два квартала подряд; ступень 1 — не требуется. Это строже формулы выше (она допускает собранность на единицу ниже ступени): соотношение — предмет калибровки, формула выше остаётся действующей.

**Согласованность — флаг, не блокер.** Разброс `vn−v1 ≥ 3` → профиль «рассогласован»: это диагностический вывод (не отдельная ступень), понижает confidence, отстающая характеристика становится приоритетом роста (наследник bottleneck). Ступень не отнимается за рассогласованность.

**Gate агентности 4→5.** Ступень 5 (Проактивный) дополнительно требует агентность ≥4. На ступенях 1-4 агентность участвует наравне со всеми характеристиками, отдельного порога нет. (При текущем составе условие следует из формулы — `min_личн ≥ 4` на ступени 5 — и сохраняется как защита на случай изменения состава.)

**§13.3а Время на новое и дополнительные условия ступени (решение пилота 15.10.2026).** Итоговая ступень = минимум из независимых расчётов: профиль характеристик (формула выше), время на новое, владение методами. Каждый расчёт даёт ступень 1–5 или `null`; неизвестное включённое условие даёт итог `null`.

Время на новое — среднее число часов в неделю на саморазвитие (учёт слотов, включая самоотчёт при закрытии дня и недели, плюс пройденные занятия; рабочее программирование не учитывается):

| Ступень | Норма |
|---|---|
| 2 | ≥ 4 ч/нед за 4 недели |
| 3 | ≥ 6 ч/нед за 8 недель |
| 4 | ≥ 10 ч/нед за 12 недель |
| 5 | ≥ 10 ч/нед за 24 недели |

Накопленных порогов часов нет. Статус условия: рекомендация и вопрос человеку, в итоговый минимум не входит до появления признака подключения учёта времени с датой начала и полнотой за окно (без такого признака «учёт не ведётся» и «ноль часов» не различимы).

Владение методами каталога (критерий — `WP-600`) в минимум не входит до утверждения минимального набора методов.

**Дыры данных — жёсткое правило, не смягчение confidence.** Нет сигнала по гейтящей характеристике (`needs_refresh`, состав — §13.1; отсутствие ясности ступень не обнуляет: она не гейтит) → `stage_v6 = null` до дозаполнения, а не расчёт с пониженной уверенностью. Действующей остаётся ступень v5 (см. `rcs_version`, §13.6). Не подставлять вымышленные значения, не маскировать заниженной точностью. (Уточнено раундом критики 13.09 — прежняя формулировка «пониженная confidence» в §13.6 не должна пониматься как альтернатива этому правилу, она про доверие к УЖЕ ПРИСВОЕННОЙ ступени, не про присвоение при дыре в данных гейтящих характеристик.)

**Частичный профиль при `stage_v6 = null` (уточнено раундом критики 13.09, п.4).** `stage_v6 = null` не означает пустой профиль на витрине: каждая характеристика состава профиля показывается своим значением или явным `null` по отдельности (какая именно характеристика создала дыру — видно), плюс все три вспомогательные — независимо от статуса `stage_v6`. Витрина не обязана «прятать» всё при отсутствии итоговой ступени; прячется только сам вывод ступени.

**Стрессоустойчивость вне состава профиля — не случайность.** Она уже `dormant-no-source` (§13.2) и отнесена к вспомогательным (§13.1) именно поэтому — если бы она гейтила, `stage_v6` был бы null постоянно, у всех, что равносильно отказу от формулы. Тот же аргумент подтверждает решение по ресурсности.

**Р1 (решение пилота 13.09, статус: реализовано 15.10.2026).** Новая формула заменит `check_rcs_stage()` при реализации сразу, без отдельного **пользовательского** параллельного поля `stage_vnext` (видимого людям, живущего в БД как второй расчёт рядом с боевым на протяжении недель) и без формального этапа сравнения на реальных профилях как **отдельного decision-gate перед переключением**. После АрхГейт и в рамках Ф3 (`WP-576`) реализация v6 атомарно переключает алгоритм; с 15.10.2026 формула действует в боевом расчёте; v5 остаётся для аккаунтов без записи в журнале ступеней (§13.6). Расхождения ловятся живой приёмкой на фазе каскада, не отдельным decision-gate ДО переключения — это решение о порядке работ и об объёме пользовательской поверхности, не отказ от обычной инженерной проверки. **Уточнение (независимая проверка 14.09, снимает найденное противоречие с картой каскада):** shadow/test-прогон нового расчёта на исторических данных ПЕРЕД переключением — стандартная инженерная практика при любой замене вычисления, не то, что отклоняет это решение; отклонён именно `stage_vnext` как отдельный долгоживущий параллельный путь с собственным decision-gate поверх него.

**Р2 (решение пилота 13.09, статус: реализовано 14.10.2026 — правка `PD.FORM.093 §5.2` карточка 4 закоммичена) — сужение формулы регулярности `PD.FORM.093 §5.2` (карточка 4, `regularity_idx`) относительно gate-вычисления перехода 4→5 (§5.4).** **Основание решения уточнено независимой проверкой 14.09 — исходная формулировка называла источником пересечения слагаемое `cp.skl`, которого в формуле регулярности нет вообще (оно в собранности, способности производить и продуктивности, §5.2 карточки 3/5/6); ниже — реальное основание.** «Регулярность» (§5.2 карточка 4) и «собранность» (§5.2 карточка 3, `composure_idx`) используют один и тот же auto-композит на входе — часы в неделю на методах саморазвития (WakaTime/LMS) и регулярность слот-планирования (`day_open_completed`/`day_close_completed`) — различаясь в основном окном наблюдения (собранность — короче, регулярность — явно 12 недель) и одним дополнительным элементом у регулярности (серия недель 4-недельной автономии, `wp_created.initiator=self` без внешних триггеров). Решение: сузить регулярность до элементов, которых нет у собранности (окно 12 недель + автономный ряд), не пересчитывая пороги перехода 4→5 и не сливая характеристики. **Это переопределение понятия, не только формулы:** регулярность в `PD.FORM.093` ранее означала «то же, что собранность, плюс более длинное окно», после правки будет означать «устойчивость и автономность на длинном горизонте», не дублируя входные сигналы собранности. Порог `≥4` и структура gate-вычисления §5.4 сохраняются. Правка формулы физически вносится в `PD.FORM.093 §5.2` отдельным коммитом — этот пункт фиксирует решение и его (исправленное) обоснование для обоих документов, актуальная формула до той правки не меняется.

### 13.3б Путь по активности (31.10.2026, решение пилота)

**Решено 31.10, не включено (в ветке activity-hub `wp602-two-paths-evaluator` за выключателем `STAGE_TWO_PATHS`, в main не влито, РП-602 Ф11).** Путь по активности считает ступень по формуле `stage = min(v2, min_личн + 1)` (§13.3) над характеристиками, которые измеряются поведением и рабочими артефактами, без срезов диагностики. Состав: **собранность, агентность, ясность**; **ясность пока необязательна** (решение пилота 15.10.2026: мост ясности даёт минимум всем, §13.3 и `OPTIONAL` в расчёте), поэтому по решению ступень пути считается по собранности и агентности (в боевом расчёте main сегодня гейтят четыре, §13.1), а ясность видна отдельно и в минимум не входит до доработки моста. Включение ясности в минимум пути меняет результаты и проверяется теневым прогоном. «Зрелость» и «системность» по определению (§13.1) проявляются в основаниях решений и системных описаниях и остаются в диагностическом пути. Ступень 5 путь по активности не присваивает (§5.1, §5.2). Правило дыр данных (§13.3): нет сигнала по характеристике пути → путь даёт `null`, а не расчёт по неполным данным; ступень тогда определяется диагностикой. Состав меняется решением пилота и проверяется теневым прогоном рядом с действующим расчётом (§13.6).

Переключение боевого расчёта идёт после теневого прогона на всех участниках с согласием: таблица «ступень до → ступень после». Первый боевой прогон не отправляет уведомлений о росте. Основание и риски — запись АрхГейта `DRR-archgate-stage-monotonic-no-gate` (РП-602).

### 13.4 Три лестницы — не путать

Модель считает только **ступень** (эта, §13.3, 5 значений, в боевом расчёте с 15.10.2026, статус draft, `implementation_status: partial`). Не то же самое, что:
- **Степень квалификации** (8 значений, Ученик→Революционер, присваивается ВНЕШНЕ методсоветом — защита + деятельность + решение комиссии, не расчётом). Gate-характеристики этой лестницы (включая «способность производить», §13.1.6) в каталог ступени не входят.
- **Охват изменений** (отдельная шкала 1-6, используется как gate перехода 4→5 в `PD.FORM.093`).

Путаница между лестницами регулярно встречается в источниках (найдено разведкой 13.09) — характеристика «способность производить» (§13.1.6) была кандидатом именно на эту путаницу: она гейтит степень квалификации, не ступень.

### 13.5 Каскад «внимание — мировоззрение — мастерство — системы»

Объяснительная проекция (не формальная привязка каждой колонки к характеристике — решение пилота 13.09, снимает нерешаемый вопрос «куда девать колонку Мастерство»). Читается по практикумам: S0 «Ритмичность» запускает Внимание; S1 «Собранность» крепит Внимание, первый заход — в Мировоззрение; S2 «Агентность» крепит Мировоззрение, первый заход — в Мастерство; S3 «Системность» крепит Мастерство, первый заход — в Системы. Рост не переключается, а накапливается — ничего не выключается по пути, ступень подтверждается по всем характеристикам сразу, не по одной.

Разрыв «имя практикума ≠ его фактический фокус» (практикумы S1/S2 по канону `WP-385` фактически целят в `cp.wld`/`cp.skl`) существовал до этой модели — живая презентация практикума «Собранность» (13.09) показывает это как осознанный кумулятивный дизайн, не как ошибку.

### 13.6 Версионирование и обратная совместимость

- `rcs_version`: `v5.0` (§1-12) и `v6` (этот раздел; боевой расчёт ступени с 15.10.2026) сосуществуют. В цифровом двойнике (`3_derived.3_4_qualification`) версия ступени указана явно полем `rcs_version` (`v6` — из журнала `learning.stage_transitions`, `v5` — прежняя лестница профилировщика для аккаунтов без записи в журнале); мост — РП-576, 20.10.2026. Существующие записи `cp_assessments` НЕ переписываются; v6-оценка — новая запись с полями `source_assessment_id`, `source_rcs_version='v5.0'`, `derivation_version='v6.mig.1'`, `derived_at`.
- **Переименования и консолидации** (например переименование шкалы делегирования, §13.1.2; консолидация агентности 13.09 отменена 21.11) — только через слой `canonical_id`+`alias_name`. **Механизм (выбран раундом критики 13.09, вариант «таблица-сателлит», не `registry-view` — второй вариант отклонён, чтобы не создавать неоднозначность реализации): не аддитивные nullable-поля в существующей `learning.characteristic_norm`** (это всё равно изменение схемы действующей таблицы + backfill), **а отдельная физическая таблица-сателлит** вида `(catalog_version, canonical_id, alias_name, legacy_key)`. Минимальные требования к её схеме до кода (уточнено раундом критики, финальный проход): первичный ключ строки `(catalog_version, canonical_id, alias_name)` даёт идентичность записи; отдельно **`UNIQUE (catalog_version, alias_name)`** — это и есть правило «один alias резолвится ровно в один canonical_id на версию каталога» (составного ключа выше для этого недостаточно — он не запрещает записать один и тот же alias с разными canonical_id). Правило кратности в другую сторону: один `canonical_id` может иметь несколько `alias_name` (например агентность: `cp.agt`, `agency_idx`, `CHR.K.001`) — это разрешено обеими схемами ключей. Записи версии `catalog_version` иммутабельны после публикации (новая консолидация — новая версия, не правка задним числом). Существующие читатели (`dt_calc.py`, `cp_assessment.py`) продолжают читать по старым ключам без изменений до отдельного решения о переключении; таблица-сателлит — это отображение поверх, не миграция первичных данных. Честная оговорка: это backward-compatible ROLLOUT, не гарантия «вообще без schema change» — переключение первичного ключа, uniqueness/FK или контрактов API на canonical-id, если оно понадобится, останется отдельным, потенциально breaking, решением на фазе реализации.
- Детерминированный derive-проход: `cp_scores` + bh-метрики → v6-профиль с полем confidence по каждой присвоенной характеристике. Confidence — про доверие к уже присвоенному значению (свежесть источника и т.п.); при отсутствии сигнала по гейтящей характеристике действует отдельное, более жёсткое правило §13.3 (`stage_v6 = null`, не «низкая confidence»).
- Присвоение ступеней 1-4: сегодня — формула §13.3 над гейтящими характеристиками с потолком агентности 4 без свежего `cp.agt`; переход блокируется, если подтверждённая диагностикой ступень ниже расчётной (двойной gate v5 в main действует до включения правила двух путей). По решению 31.10 (§5.1, не включено) — два независимых пути, диагностика не удерживает. Ступень 5: формула §13.3 при высоких четырёх характеристиках может дать 5, но запись возможна только при cp-ступени не ниже 5 и свежем `cp.agt` = 5 (сегодня — пятёрки по всем пяти срезам, решение 20.10); «только через диагностику и составной gate §5.2» — текст §5.1 (31.10) и приёмка 20.10; части (ii) и (iii) gate §5.2 в коде не реализованы ни в main, ни в ветке. Рассогласованность профиля остаётся флагом (§13.3: «Согласованность — флаг, не блокер»).
